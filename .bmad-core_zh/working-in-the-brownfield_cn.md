# 在老旧系统中工作：完整指南

> **强烈推荐：使用 Gemini Web 或 Gemini CLI 生成老旧系统文档！**
>
> Gemini Web 的 1M+ 令牌上下文窗口或 Gemini CLI（当它正常工作时）可以一次性分析您的整个代码库，或其中的关键部分（显然在合理范围内）：
>
> - 通过 GitHub URL 上传或在项目文件夹中使用 gemini cli
> - 如果在 Web 中工作：使用 `npx bmad-method flatten` 将您的项目展平为单个文件，然后将该文件上传到您的 Web 代理。

## 什么是老旧系统开发？

老旧系统开发是指向现有软件项目添加功能、修复错误或进行现代化改造。与绿地（新）项目不同，老旧系统工作需要理解现有代码、尊重限制，并确保新更改无缝集成，而不会破坏现有功能。

## 何时使用 BMad 进行老旧系统开发

- 为现有应用程序添加重要新功能
- 现代化旧代码库
- 集成新技术或服务
- 重构复杂系统
- 修复需要架构理解的错误
- 记录未文档化的系统

## 何时不使用老旧系统流程

如果您刚刚完成了使用 BMad 的 MVP，并且想继续进行 MVP 后续工作，那么更简单的方法是直接与产品经理沟通，请求他们与您合作创建一个新的史诗添加到 PRD 中，拆分该史诗，与架构师一起更新任何架构文档，然后从那里继续。

## 完整的老旧系统工作流

1. **按照 [<ins>用户指南 - 安装</ins>](user-guide.md#installation) 步骤在 Web 中设置您的代理。**
2. **生成整个代码库的“扁平化”单个文件** 运行：`npx bmad-method flatten`

### 选择您的方法

#### 方法 A：PRD 优先（如果添加非常大且复杂的新功能、单个或多个史诗或大量更改，建议使用）

**最适合**：大型代码库、单体仓库，或者当您确切知道要构建什么时

1. **首先创建 PRD** 以定义需求
2. **仅根据 PRD 需求记录相关区域**
3. **更高效** - 避免记录未使用的代码

#### 方法 B：文档优先（适合小型项目）

**最适合**：小型代码库、未知系统或探索性更改

1. **首先记录整个系统**
2. **创建包含完整上下文的 PRD**
3. **更彻底** - 捕获所有内容

### 方法 A：PRD 优先工作流（推荐）

#### 阶段 1：首先定义需求

**在 Gemini Web 中（上传您的 flattened-codebase.xml）：**

```bash
@pm
*create-brownfield-prd
```

产品经理将：

- **询问您的增强需求**
- **探索代码库**以了解当前状态
- **识别需要文档的受影响区域**
- **创建具有明确范围的重点 PRD**

**关键优势**：PRD 确定了您的单体仓库/大型代码库中实际需要文档的部分！

#### 阶段 2：重点文档

**仍在 Gemini Web 中，现在具有 PRD 上下文：**

```bash
@architect
*document-project
```

分析师将：

- 如果未提供 PRD，则**询问您的重点**
- **提供选项**：创建 PRD、提供需求或描述增强功能
- **参考 PRD/描述**以理解范围
- **关注 PRD 或您的描述中识别出的相关模块**
- **跳过不相关的区域**以使文档精简
- **为所有环境生成一份架构文档**

分析师创建：

- **一份遵循 fullstack-architecture 模板的全面架构文档**
- **涵盖所有系统方面**在一个文件中
- **易于复制和保存**为 `docs/project-architecture.md`
- 如果需要，**以后可以在 IDE 中拆分**

例如，如果您说“向用户服务添加支付处理”：

- 仅文档：用户服务、API 端点、数据库模式、支付集成
- 创建显示仅与支付相关的代码路径的重点源代码树
- 跳过：管理面板、报告模块、不相关的微服务

### 方法 B：文档优先工作流

#### 阶段 1：文档化现有系统

**最佳方法 - 具有 1M+ 上下文的 Gemini Web**：

1. **转到 Gemini Web** (gemini.google.com)
2. **上传您的项目**：
   - **选项 A**：直接粘贴您的 GitHub 仓库 URL
   - **选项 B**：上传您的 flattened-codebase.xml 文件
3. **加载分析师代理**：上传 `dist/agents/architect.txt`
4. **运行文档**：输入 `*document-project`

分析师将生成所有内容的全面文档。

#### 阶段 2：规划您的增强功能

##### 选项 A：完整老旧系统工作流（建议用于重大更改）

**1. 创建老旧系统 PRD**：

```bash
@pm
*create-brownfield-prd
```

产品经理代理将：

- **分析现有文档**（来自阶段 1）
- **向您请求具体的增强细节**
- **评估复杂性**并推荐方法
- **创建增强功能的史诗/故事结构**
- **识别风险和集成点**

**产品经理代理如何获取项目上下文**：

- 在 Gemini Web 中：已从阶段 1 文档中获取完整的项目上下文
- 在 IDE 中：将询问“请提供现有项目文档的路径”

**您将遇到的关键提示**：

- “您想添加什么具体的增强或功能？”
- “这需要与任何现有系统或 API 集成吗？”
- “我们必须尊重哪些关键限制？”
- “您的时间表和团队规模是多少？”

**2. 创建老旧系统架构**：

```bash
@architect
*create-brownfield-architecture
```

架构师将：

- **审查老旧系统 PRD**
- **设计集成策略**
- 如果需要，**规划迁移方法**
- **识别技术风险**
- **定义兼容性要求**

##### 选项 B：快速增强（用于重点更改）

**对于没有完整 PRD 的单个史诗**：

```bash
@pm
*create-brownfield-epic
```

在以下情况下使用：

- 增强功能定义明确且独立
- 现有文档全面
- 更改不影响多个系统
- 您需要快速周转

**对于单个故事**：

```bash
@pm
*create-brownfield-story
```

在以下情况下使用：

- 错误修复或微小功能
- 非常独立的更改
- 没有架构影响
- 清晰的实施路径

### 阶段 3：验证规划工件

```bash
@po
*execute-checklist-po
```

产品负责人确保：

- 与现有系统的兼容性
- 没有计划破坏性更改
- 风险缓解策略到位
- 清晰的集成方法

### 阶段 4：保存和拆分文档

1. 将您的 PRD 和架构保存为：
   docs/brownfield-prd.md
   docs/brownfield-architecture.md
2. 拆分您的文档：
   在您的 IDE 中

   ```bash
   @po
   shard docs/brownfield-prd.md
   ```

   ```bash
   @po
   shard docs/brownfield-architecture.md
   ```

### 阶段 5：过渡到开发

**遵循 [<ins>增强型 IDE 开发工作流</ins>](enhanced-ide-development-workflow.md)**

## 老旧系统最佳实践

### 1. 始终先文档化

即使您认为您了解代码库：

- 运行 `document-project` 以捕获当前状态
- AI 代理需要此上下文
- 发现未文档化的模式

### 2. 尊重现有模式

老旧系统模板专门查找：

- 当前编码约定
- 现有架构模式
- 技术限制
- 团队偏好

### 3. 计划逐步推出

老旧系统更改应：

- 支持功能标志
- 计划回滚策略
- 包括迁移脚本
- 保持向后兼容性

### 4. 彻底测试集成

测试重点关注：

- 集成点
- 现有功能（回归）
- 性能影响
- 数据迁移

### 5. 沟通更改

文档：

- 更改了什么以及为什么
- 迁移说明
- 引入的新模式
- 弃用通知

## 常见老旧系统场景

### 场景 1：添加新功能

1. 文档化现有系统
2. 创建侧重于集成的老旧系统 PRD
3. 架构强调兼容性
4. 故事包括集成任务

### 场景 2：现代化遗留代码

1. 广泛的文档化阶段
2. PRD 包括迁移策略
3. 架构规划逐步过渡
4. 故事遵循绞杀者模式

### 场景 3：复杂系统中的错误修复

1. 文档化相关子系统
2. 使用 `create-brownfield-story` 进行重点修复
3. 包括回归测试要求
4. QA 验证无副作用

### 场景 4：API 集成

1. 文档化现有 API 模式
2. PRD 定义集成要求
3. 架构确保一致的模式
4. 故事包括 API 文档更新

## 故障排除

### “AI 不理解我的代码库”

**解决方案**：重新运行 `document-project`，并指定更具体的文件路径

### “生成的计划不符合我们的模式”

**解决方案**：在规划阶段之前，使用您的特定约定更新生成的文档

### “小改动样板太多”

**解决方案**：使用 `create-brownfield-story` 代替完整工作流

### “集成点不明确”

**解决方案**：在 PRD 创建过程中提供更多上下文，特别强调集成系统

```bash
# 文档化现有项目
@architect → *document-project

# 创建增强 PRD
@pm → *create-brownfield-prd

# 创建专注于集成的架构
@architect → *create-brownfield-architecture

# 快速史诗创建
@pm → *create-brownfield-epic

# 单个故事创建

```

### 决策树

```text
您有大型代码库或单体仓库吗？
├─ 是 → PRD 优先方法
│   └─ 创建 PRD → 仅文档化受影响的区域
└─ 否 → 您对代码库熟悉吗？
    ├─ 是 → PRD 优先方法
    └─ 否 → 文档优先方法

这是影响多个系统的重大增强吗？
├─ 是 → 完整老旧系统工作流
└─ 否 → 这不仅仅是简单的错误修复吗？
    ├─ 是 → brownfield-create-epic
    └─ 否 → brownfield-create-story
```

## 结论

使用 BMad-Method 进行老旧系统开发，在修改现有系统时提供了结构和安全性。关键在于通过文档提供全面的上下文，使用考虑集成要求的专用模板，并遵循尊重现有约束同时实现进展的工作流。

记住：**先文档化，仔细规划，安全集成**
