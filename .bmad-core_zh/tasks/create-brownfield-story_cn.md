# 创建老项目故事任务

## 目的

为非常小的老项目增强功能创建单个用户故事，这些增强功能可以在一次集中的开发会话中完成。此任务适用于需要现有系统集成意识的最小添加或错误修复。

## 何时使用此任务

**在以下情况下使用此任务：**

- 增强功能可以在单个故事中完成
- 不需要新的架构或重要的设计
- 更改完全遵循现有模式
- 集成直接且风险最小
- 更改是孤立的，边界清晰

**在以下情况下使用 brownfield-create-epic：**

- 增强功能需要 2-3 个协调的故事
- 需要一些设计工作
- 涉及多个集成点

**在以下情况下使用完整的老项目 PRD/架构流程：**

- 增强功能需要多个协调的故事
- 需要架构规划
- 需要大量的集成工作

## 任务执行指令

### 0. 文档上下文

按此顺序检查可用文档：

1. **分片 PRD/架构** (docs/prd/, docs/architecture/)
   - 如果找到，建议改用 create-next-story 任务

2. **老项目架构文档** (docs/brownfield-architecture.md 或类似文件)
   - 由 document-project 任务创建
   - 包含实际系统状态、技术债务、变通方法

3. **老项目 PRD** (docs/prd.md)
   - 可能包含嵌入式技术细节

4. **Epic 文件** (docs/epics/ 或类似文件)
   - 由 brownfield-create-epic 任务创建

5. **用户提供的文档**
   - 要求用户指定位置和格式

### 1. 故事识别和上下文收集

#### 1.1 识别故事来源

根据可用文档：

- **从老项目 PRD**：从 Epic 部分提取故事
- **从 Epic 文件**：读取 Epic 定义和故事列表
- **从用户指示**：询问用户要实施哪个特定增强功能
- **没有明确来源**：与用户协作定义故事范围

#### 1.2 收集必要上下文

关键：对于老项目故事，您“必须”收集足够的上下文以确保安全实施。准备好向用户询问缺失信息。

**所需信息清单：**

- [ ] 现有功能可能受到哪些影响？
- [ ] 与当前代码的集成点是什么？
- [ ] 应遵循哪些模式（带示例）？
- [ ] 存在哪些技术约束？
- [ ] 是否有任何“陷阱”或需要了解的变通方法？

如果缺少任何所需信息，请列出缺失信息并要求用户提供。

### 2. 从可用来源提取技术上下文

#### 2.1 从 Document-Project 输出

如果使用来自 document-project 的 brownfield-architecture.md：

- **技术债务部分**：记录任何影响此故事的变通方法
- **关键文件部分**：识别需要修改的文件
- **集成点**：查找现有集成模式
- **已知问题**：检查故事是否触及有问题区域
- **实际技术栈**：验证版本和约束

#### 2.2 从老项目 PRD

如果使用老项目 PRD：

- **技术约束部分**：提取所有相关约束
- **集成要求**：记录兼容性要求
- **代码组织**：遵循指定模式
- **风险评估**：了解潜在影响

#### 2.3 从用户文档

要求用户帮助识别：

- 相关技术规范
- 要遵循的现有代码示例
- 集成要求
- 项目中使用的测试方法

### 3. 渐进式故事创建

#### 3.1 创建初始故事结构

从故事模板开始，填写已知内容：

```markdown
# 故事 {{增强标题}}

## 状态：草稿

## 故事

作为 {{用户类型}}，
我想要 {{增强功能}}，
以便 {{交付价值}}。

## 上下文来源

- 源文档：{{文档名称/类型}}
- 增强类型：{{单个功能/错误修复/集成/等}}
- 现有系统影响：{{简要评估}}
```

#### 3.2 制定验收标准

关键：对于老项目，始终包含有关维护现有功能的标准

标准结构：

1. 新功能按指定工作
2. 现有 {{受影响功能}} 继续不变地工作
3. 与 {{现有系统}} 的集成保持当前行为
4. {{相关区域}} 没有回归
5. 性能保持在可接受范围内

#### 3.3 收集技术指导

关键：如果信息缺失，您需要在此处与用户交互

使用可用信息创建开发技术指导部分：

````markdown
## 开发技术指导

### 现有系统上下文

[从可用文档中提取]

### 集成方法

[根据找到的模式或询问用户]

### 技术约束

[从文档或用户输入中提取]

### 缺失信息

关键：列出开发人员将需要但您找不到的任何内容，并要求提供缺失信息

### 4. 包含安全检查的任务生成

#### 4.1 生成实施任务

根据收集的上下文，创建以下任务：

- 如果系统理解不完整，则包括探索任务
- 添加现有功能的验证任务
- 包括回滚考虑
- 在已知时引用特定文件/模式

老项目任务结构示例：

```markdown
## 任务 / 子任务

- [ ] 任务 1：分析现有 {{组件/功能}} 实施
  - [ ] 审查 {{特定文件}} 以了解当前模式
  - [ ] 文档集成点
  - [ ] 识别潜在影响

- [ ] 任务 2：实施 {{新功能}}
  - [ ] 遵循 {{示例文件}} 中的模式
  - [ ] 与 {{现有组件}} 集成
  - [ ] 保持与 {{约束}} 的兼容性

- [ ] 任务 3：验证现有功能
  - [ ] 测试 {{现有功能 1}} 是否仍然有效
  - [ ] 验证 {{集成点}} 行为未改变
  - [ ] 检查性能影响

- [ ] 任务 4：添加测试
  - [ ] 遵循 {{项目测试模式}} 的单元测试
  - [ ] {{集成点}} 的集成测试
  - [ ] 如果需要，更新现有测试
```
````

### 5. 风险评估和缓解

关键：对于老项目 - 始终包含风险评估

添加老项目特定风险部分：

```markdown
## 风险评估

### 实施风险

- **主要风险**：{{对现有系统的主要风险}}
- **缓解**：{{如何解决}}
- **验证**：{{如何确认安全}}

### 回滚计划

- {{撤销更改的简单步骤（如果需要）}}

### 安全检查

- [ ] 现有 {{功能}} 在更改前已测试
- [ ] 更改可以进行功能标记或隔离
- [ ] 回滚程序已文档化
```

### 6. 最终故事验证

在最终确定之前：

1. **完整性检查**：
   - [ ] 故事具有明确的范围和验收标准
   - [ ] 技术上下文足以支持实施
   - [ ] 集成方法已定义
   - [ ] 风险已识别并得到缓解

2. **安全检查**：
   - [ ] 现有功能保护已包含
   - [ ] 回滚计划可行
   - [ ] 测试涵盖新功能和现有功能

3. **信息空白**：
   - [ ] 从用户那里收集了所有关键缺失信息
   - [ ] 剩余未知因素已为开发代理记录
   - [ ] 在需要时添加了探索任务

### 7. 故事输出格式

以适当的命名保存故事：

- 如果来自 Epic：`docs/stories/epic-{n}-story-{m}.md`
- 如果独立：`docs/stories/brownfield-{feature-name}.md`
- 如果顺序：遵循现有故事编号

包含注明文档上下文的标题：

```markdown
# 故事：{{标题}}

<!-- 来源：{{使用的文档类型}} -->
<!-- 上下文：对 {{现有系统}} 的老项目增强 -->

## 状态：草稿

[故事内容的其余部分...]
```

### 8. 移交沟通

向用户提供明确的移交：

```text
老项目故事已创建：{{故事标题}}

源文档：{{使用的文档}}
故事位置：{{文件路径}}

已识别的关键集成点：
- {{集成点 1}}
- {{集成点 2}}

已注意到的风险：
- {{主要风险}}

{{如果信息缺失}}：
注意：一些技术细节不清楚。故事包括探索任务，用于在实施期间收集所需信息。

下一步：
1. 审查故事的准确性
2. 验证集成方法是否与您的系统一致
3. 批准故事或请求调整
4. 开发代理即可实施并进行安全检查
```

## 成功标准

老项目故事创建成功，满足以下条件：

1. 故事可以在不要求开发人员搜索多个文档的情况下实施
2. 集成方法清晰且对现有系统安全
3. 所有可用的技术上下文均已提取和组织
4. 缺失信息已识别并得到处理
5. 风险已文档化并附有缓解策略
6. 故事包含现有功能验证
7. 回滚方法已定义

## 重要说明

- 此任务专门针对具有非标准文档的老项目
- 始终优先考虑现有系统稳定性而不是新功能
- 如果有疑问，请添加探索和验证任务
- 最好向用户寻求澄清，而不是凭空假设
- 每个故事都应独立，以便开发代理处理
- 在可用时包含对现有代码模式的引用
